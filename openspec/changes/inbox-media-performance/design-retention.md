# Design addendum: 90-day chat-media retention (slice 8)

Addendum to `design.md`. Covers the `chat-media-retention` capability only. Resolves tasks T8.1 and supplies the shape T8.2–T8.6 held as a proposal.

## Context

`chat-media` held 875 MB on 2026-11-27 and grows ~200 MB per month against the Supabase free-plan 1 GB ceiling. Without retention the bucket fills in about a month and new media stops being stored. Owner decision: delete media objects older than 90 days, keep every message row and all message text.

## Decisions

### D-R1 — Age source: `storage.objects.created_at`

The cutoff uses the object's creation timestamp, not `last_modified`. Paths are unique per ingest (`account-<id>/<ts>-wa-<mediaId>.<ext>`), so an object is never re-uploaded in place; `created_at` therefore matches ingest time and is stable. `last_modified` is rejected because a metadata touch would silently extend an object's life.

Rejected alternative: deriving age from the source message's `created_at`. It needs a join per candidate and would delete media that was re-ingested later (backfill copies), which is not what the owner asked.

### D-R2 — Selection is SQL, deletion is the Storage API

- Candidates are selected with the service role against `storage.objects` (`bucket_id = 'chat-media'`, `created_at < now() - interval '<days> days'`).
- `pending` media is exempt: candidates exclude any path referenced by a message whose media status is `pending`. Matching uses the stored path (`split_part(media_url, '/chat-media/', 2)`), the same derivation the backfill uses.
- Deletion goes through `storage.remove(paths)`, never `DELETE FROM storage.objects`. Direct row deletion bypasses Storage bookkeeping and can leave orphaned objects or a desynced bucket.

### D-R3 — Batches, cap and idempotency

- Per run: select at most `MEDIA_RETENTION_MAX_PER_RUN` candidates (default 500), delete in batches of 100 (the Storage remove limit), then stop. The next run continues from the remainder; no cursor is stored because the next selection query naturally excludes deleted objects.
- Two runs on the same day delete nothing extra: the second run's candidates were either deleted or are still `pending`.
- A failure mid-run deletes only the batches already confirmed; the run reports the confirmed count.

### D-R4 — Configuration

Environment variables, read at call time, validated at startup of the job:

| Variable | Default | Invalid values |
|---|---|---|
| `MEDIA_RETENTION_DAYS` | 90 | Non-integer or < 30 → job refuses and reports |
| `MEDIA_RETENTION_MAX_PER_RUN` | 500 | Non-integer or < 1 → job refuses and reports |
| `MEDIA_RETENTION_DRY_RUN` | unset (false) | Only `1`/`true` enable dry run |

A dry run performs the full selection, logs the candidate paths count and bytes, and calls no deletion.

### D-R5 — Scheduling

The job runs inside the existing `/api/cron/webhook-outbox` worker, after the outbox flush, guarded by the same cron authentication. No new route, no new cron job. It is sequential and bounded so it never delays the outbox flush beyond its cap.

Order matters: outbox first, retention second. If the outbox flush fails, retention is skipped for that tick.

### D-R6 — Thumbnails

Each deleted original deletes its thumbnail sibling in the same call. The thumbnail path is derived with the naming convention from `design.md`; if the sibling does not exist the deletion is still reported as success. No orphan thumbnails are left behind, and an orphan thumbnail found without its original is deleted too.

### D-R7 — Unavailable media in the panel

A purged object is a third media state, distinct from `pending` and from `failed`:

- The signed URL request for a missing object fails; the bubble renders the "unavailable" state, not a broken image, not an infinite spinner, and logs no console error.
- `media_url` is never modified by retention, so every existing reader keeps working and the failure is discovered at fetch time.
- The state is reached through the existing signed-media resolution path; no new API is added.

### D-R8 — Access model untouched

Retention runs with the service role and never creates, modifies or shares URLs. `chat-media` stays private and members-only per migration 261. No signed URL is generated by the job.

## Rollback

Remove the retention call from the cron worker and redeploy. Deleted objects are gone (that is the point of the change); everything else is unaffected: message rows, text, `media_url` and the private-bucket model are never written by this slice.
